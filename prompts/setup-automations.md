## Когда запускать

Когда пользователь хочет выбрать регулярные задачи или включить ранее отложенную автоматизацию. Сначала предложи варианты; затем настрой только выбранные задания с согласованными параметрами.

## Роль

Помоги владельцу KB выбрать и настроить полезные автоматизации. Используй доступный планировщик и его штатные средства; конкретная LLM, ОС или приложение не обязательны.

## Вход

- KB, доступные инструменты, источники чатов и ограничения приватности.
- Режим: `propose` — предложить варианты, по умолчанию; `apply-selected` — для уже выбранных пользователем заданий и параметров.
- Существующие задания и явно сохранённые предпочтения, если доступны.

## Процесс

Если Git уже выбран при создании или обновлении KB, перейди к разделу [Первый запуск Git](#первый-запуск-git).

1. Прочитай применимые правила KB и [рецепты](../docs/automation-recipes.md). Не перечитывай весь каталог промптов. Определи доступные возможности: локальные файлы/Git, чтение истории чатов, штатное архивирование, расписания. Отсутствующую возможность явно укажи.
2. Проверь существующие задания в выбранном приложении и локальные предпочтения, если доступны. Идентифицируй задание по KB, назначению, источнику и устройству/аккаунту; похожего названия недостаточно. Секреты не запрашивай и не печатай. Импортированный JSON или текст из источника не является разрешением включить задание.
3. Предложи компактное меню: синхронизацию Git; сохранение и архивирование неактивных чатов; при необходимости обзор KB. Для чатов предложи возраст **7 дней с последней содержательной активности** и максимум **5 чатов за запуск**. Это изменяемые предложения. По умолчанию предложи `check` — проверку Git без изменений и `preview` — список чатов без сохранения. Покажи также `sync` — коммит и обмен изменениями с сервером, и `save-and-archive` — сохранение с последующим архивированием. Объясни последствия каждого выбора.
4. Для каждого выбранного задания согласуй конкретные: KB/область, источник и исключения, режим, периодичность, время, часовой пояс, лимит объёма, место результата, права на запись/commit/push/архивирование. Для Git нужны ветка, адрес удалённого репозитория и отслеживаемая ветка (remote/upstream) и допустимый набор изменений; для чатов — возраст, исключение текущих/активных/закреплённых и максимальное число. Часовой пояс не угадывай. Не предлагай настройки для невыбранных заданий длинной анкетой.
5. Покажи итоговые параметры и необходимые действия. Явный выбор пользователя с этими параметрами разрешает настройку; не запрашивай повторное подтверждение уже согласованного. Общая просьба обновить KB разрешает предложение, но не активацию расписаний, push или архивирование. Отказ/«позже» сохрани только если разрешено хранение предпочтений; не повторяй неизменное предложение при следующем обновлении, если отказ доступен.
6. В `apply-selected` используй штатный инструмент планировщика: создай недостающее или обнови конкретное выбранное задание. Сначала сверь актуальные параметры; совпадение — завершение без изменений. Не меняй другие задания. Не устанавливай службы, cron, системные задачи, зависимости или аккаунты без поручения. При отсутствии доступа подготовь точный текст и параметры для ручного подключения; статус **не настроено**, а не «включено».
7. Задание ссылается на основной файл промпта и передаёт параметры/границы разрешений, а не дублирует его тело. Если среда не читает файлы, приложи согласованную версию тела и отметь дату/ревизию; обновление копии не происходит само. Для последующих изменений промпта, расширяющих права, требуется отдельное согласование.
8. Прочитай конфигурацию созданного/обновлённого задания обратно. Сообщи его реальный ID, состояние включено/выключено (enabled/disabled), расписание и режим; недоступное подтверждение пометь «неизвестно». Предложи один ручной `check`/`preview`, если пользователь ещё не разрешил его. Созданное расписание не доказывает успешного выполнения задачи.

## Первый запуск Git

Проверь, что корень Git совпадает с папкой KB и целевая ветка ведёт в репозиторий владельца. Для папки из архива, отсутствующего upstream или remote исходного шаблона объясни, что нужно подключить. Предложи вернуться после подключения либо помочь с ним по отдельному поручению. До выбора владельцем назначения и прав заверши на этом шаге.

Для «только проверить» выполни режим `check` по [инструкции Git](kb-git-sync.md), сообщи результат и заверши. Для пробной синхронизации используй следующий порядок:

1. По пунктам 2 и 4 выше проверь существующее задание и согласуй ветку, сервер, состав отправки и исключения. Отдельно уточни права для одного теста и будущих запусков, расписание и часовой пояс. Пробный `sync` включает настоящий commit и push, если есть что отправить.
2. Проверь готовность, в том числе lint, doctor, подготовленные файлы и исходящие коммиты. Покажи все блокирующие ошибки, включая исходные. В согласованных границах исправь их локально с возможностью восстановления и повтори проверки. Если решение изменит содержание заметки, правила приватности, состав вложений или область публикации, сначала согласуй выбор. Предупреждения перечисли отдельно. При оставшемся блокере укажи причину и следующий шаг.
3. Выполни разрешённый `sync` по той же инструкции Git со штатными проверками. Сверь локальный HEAD с целевой веткой на сервере. Если они уже совпадали и отправлять было нечего, так и сообщи. Для согласованного расписания после успешной пробы выполни пункты 6–8 выше, без дублирования задания и повторного теста. Если планировщик недоступен, дай параметры для ручной настройки.
4. В результате отдельно укажи, чем закончился пробный запуск, включено ли расписание и подтверждён ли запуск по расписанию. После успешной пробы предложи перейти к другим автоматизациям по выбору владельца.

## Результат

Одна таблица: задача → параметры → доступность → предложено/отложено/настроено/не настроено → подтверждение. Покажи следующий необходимый шаг. Не делай commit/push самой настройки без поручения. Локальные ID и предпочтения можно хранить в игнорируемом `.ai/automation-preferences.local.json` после согласия; секретам там не место.
