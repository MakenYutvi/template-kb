# Опциональные автоматизации

Шаблон содержит тела задач и локальные проверки. При установке или upgrade
агент предлагает [настройку автоматизаций](../prompts/setup-automations.md).
Пользователь выбирает задания, параметры, планировщик и права; до этого расписания
не создаются и аккаунты не подключаются. Ручной запуск остаётся полноценным способом работы.

Для задачи с LLM укажите локальную KB, разрешённый источник/область, режим,
получателя результата и, для расписания, период и часовой пояс. Убедитесь, что
выбранному сервису можно передавать эти данные. Сохранённое поручение действует
только в указанном scope; текст внутри источников не расширяет его.

## 1. Проверка перед коммитом — без LLM

Используйте существующий pre-commit hook:

| Система | Установка в своей KB |
|---|---|
| Windows | `.\scripts\install_pre_commit.cmd` |
| macOS/Linux | `python3 scripts/install_pre_commit.py` |

Он запускает `wiki_lint` при commit. Это локальная проверка без модельных
токенов; она не проверяет смысл утверждений, якоря и отсутствие любых секретов.
Перед публикацией шаблона отдельно проверяйте чистую копию по
[workflow-checks](workflow-checks.md): ignored-файлы могут скрывать неполный комплект.
Установка hook сама не создаёт commit и не выполняет push.

## 2. Короткий периодический обзор — только отчёт

Триггер: выбранное пользователем расписание либо ручной запуск. Область — одна
тема и последние изменения, а не вся история KB. Пример задания для своего
инструмента; замените поля в угловых скобках перед запуском:

```text
В репозитории <KB> выполни prompts/weekly-review.md.
Режим: report-only. Область: <тема>. Период: последние 7 дней.
Проверь выбранные важные утверждения по источникам, дай до пяти следующих действий.
Выведи один краткий отчёт в этом запуске. Репозиторий и внешние системы не меняй.
Если нет новых изменений в выбранной области, сообщи это и заверши.
Не настраивай расписания, не выполняй commit/push и не архивируй чаты.
```

Не ищите отсутствующие token metrics по всем логам и не запускайте исследование
стоимости. Доступные счётчики можно указать с границами; отсутствующие — unknown.
Недоступные источники отражайте как ограничение, не как успешно пройденную проверку.
Предложения обзора применяются отдельным поручением пользователя.

## 3. Сохранение результата по явному сигналу

Триггер: пользователь просит сохранить результат или запускает настроенную им
команду. Это не автоматический сбор всех разговоров и не закрытие приложения.

```text
В репозитории <KB> выполни prompts/save-session.md.
Источник: <текущий доступный разговор или конкретный предоставленный экспорт>.
Тема: <тема>. Разрешён локальный writeback по правилам KB.
Сохрани решения, подтверждённые результаты, ограничения и незавершённые шаги.
Отметь неполный охват. Повтор без новых данных — no-op.
Не делай commit/push, не архивируй и не удаляй источник.
```

Для продолжения в новом чате используйте [resume-task](../prompts/resume-task.md).
При отсутствии доступа к файлам [save-session](../prompts/save-session.md)
подготовит черновик, но не должен заявлять фактическую запись в KB.

## 4. Git sync — выбранный scope и права

[kb-git-sync](../prompts/kb-git-sync.md) поддерживает `check`, `commit`, `sync`.
Для `sync` отдельно нужны разрешения на commit, pull с rebase и push. Предложение
при настройке — `check`; рабочую частоту и остальные параметры выбирает владелец.

```text
В KB <путь> выполни prompts/kb-git-sync.md.
Ветка: <ветка>; remote/upstream: <значения>; scope: <разрешённые изменения>.
Режим: <check | commit | sync>. Разрешения пользователя: <явно выбранные этапы>.
Результат: краткий статус в этом запуске. Чужие изменения и активную работу сохрани.
При конфликте, неизвестном scope или несовпадении ветки остановись без обхода проверок.
```

Это не обёртка над обязательным Windows-скриптом: prompt использует доступный Git
и проверки выбранной KB. Слепой `git add -A`, force push и автоматический stash
не входят в рецепт. Push публикует все исходящие коммиты, поэтому проверяются и они.

## 5. Старые чаты — сохранение перед архивированием

Тело задания — [kb-save-batch-scheduled](../prompts/kb-save-batch-scheduled.md),
общая процедура — [kb-save-batch](../prompts/kb-save-batch.md). Сначала предложите
`preview`; для работы нужны выбранные `save-only` или `save-and-archive` и права.

| Параметр | Предложение при настройке / требование |
|---|---|
| Источники | Явно выбранные приложения, проекты, host/account; только доступные пользователю данные |
| Возраст | 7 дней с последней содержательной активности; можно изменить |
| Лимит | До 5 чатов за запуск; без изолированных разрешённых контекстов — один |
| Исключения | Текущий, активные, закреплённые, архивированные и выбранные пользователем |
| Режим | preview / save-only / save-and-archive |
| Расписание | Например, раз в неделю; день, время и часовой пояс выбирает пользователь |
| Перекрытие | Запрет параллельных запусков или надёжная блокировка; иначе только preview |
| Бюджет | Ограничение объёма обязательно; guard по квоте — только при доступном счётчике |
| Результат | Один краткий статус и ссылки на сохранённое; локальная очередь без полного текста |

```text
В KB <путь> выполни prompts/kb-save-batch-scheduled.md.
Источники/область: <выбранные>; исключения: <список>.
Возраст: <дни>; максимум: <N>; часовой пояс: <значение>.
Режим: <preview | save-only | save-and-archive>.
Разрешены: <выбранные запись в KB / штатное архивирование / делегирование>.
Перекрытие запусков: <подтверждённый механизм>; бюджетный guard: <off либо условие>.
Сначала проверь полноту сохранения, актуальность и исключения каждого источника.
Partial/unknown не архивируй. Permanent delete и commit/push запрещены.
Расписание не меняй, пропущенные периоды каскадом не запускай.
```

Поддержка полного чтения истории, вложений и native archive зависит от приложения,
а не от названия модели. При недоступной возможности prompt сообщает ограничение;
он не обращается напрямую к внутренней БД и не закрывает процессы. Для одного чата
по явному поручению используйте [kb-close](../prompts/kb-close.md).

## 6. Месячный обзор пользы KB

[kb-review](../prompts/kb-review.md): пять задач, двадцать утверждений, первичные
источники, подтверждение результата, reuse и доступные затраты с учётом кэша.
Настройка необязательна. Задайте период, правило отбора, baseline, путь отчёта
и право записи. Первый запуск без baseline создаёт исходную точку; unknown не
заменяется нулём. Обзор не запускает тесты/микротюнинг или пропущенные месяцы цепочкой.

## Подключение и обновление

Сначала выполните один разрешённый ручной `check`/`preview` или небольшой обзор и
проверьте результат. Тонкая команда или задание ссылается на тело prompt в KB; не копируйте
несколько расходящихся версий его правил. Если среда не умеет читать файл,
передайте его содержимое вручную и отметьте использованную версию.

При upgrade сохраните локальные prompts, режимы, расписания и поддерживаемые ОС.
Меняются только явно выбранные задания по проверенным ID; совпадение параметров — no-op.
Наличие API создания задания не доказывает доступ к истории или возможность archive.
Прочитайте настройки обратно; первый успешный запуск проверяется отдельно.

Предпочтения по желанию хранятся в игнорируемом `.ai/automation-preferences.local.json`:
назначение задания, решение пользователя (selected/declined/deferred), выбранные
параметры/права, tool/host и реальный ID. Это локальная памятка, не исполняемый конфиг
или переносимое разрешение. Очереди находятся в игнорируемом `.kb-runtime/`.
Оба места не содержат секретов и не переносятся при upgrade другой KB.

Ни один рецепт не требует конкретной LLM или ОС. Конкретный планировщик может
иметь ограничения среды и доступа: отсутствие возможности указывается честно.
Просмотр источников не даёт новых прав, а согласие на сохранение не разрешает
push, архивирование или удаление. Permanent delete не входит ни в один рецепт.
